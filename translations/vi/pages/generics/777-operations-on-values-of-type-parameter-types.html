Các phép toán trên các giá trị thuộc kiểu type parameter

Chương này sẽ nói về những phép toán nào trên các giá trị của type parameter là hợp lệ và những phép toán nào không hợp lệ trong thân function generic.

Trong thân một function generic, một phép toán trên một giá trị của type parameter chỉ hợp lệ khi nó hợp lệ với các giá trị của mọi kiểu trong type set của constraint của type parameter đó. Trong thiết kế và triển khai generic tùy chỉnh hiện tại (Go 1.25), chiều ngược lại không phải lúc nào cũng đúng. Phải đáp ứng thêm một số yêu cầu để phép toán hợp lệ.

Hiện tại có nhiều hạn chế như vậy. Một số là tạm thời và có thể được loại bỏ trong các phiên bản Go tương lai, một số là vĩnh viễn. Các hạn chế tạm thời chủ yếu do khối lượng công việc triển khai gây ra, nên sẽ cần thêm thời gian và công sức để cuối cùng loại bỏ chúng. Các hạn chế vĩnh viễn do những nguyên tắc thiết kế generic tùy chỉnh gây ra.

Nội dung sau đây của chương này sẽ liệt kê các hạn chế đó. Một số sự thật và khái niệm liên quan cũng sẽ được liệt kê.

Mỗi giá trị có kiểu phải có một kiểu được xác định, các giá trị được dùng trong function generic cũng vậy

Như đã đề cập trong chương trước, kể từ Go 1.18, các kiểu giá trị trong Go có thể được phân thành hai nhóm:

  • kiểu type parameter: các kiểu được khai báo trong danh sách type parameter.
  • kiểu thông thường: các kiểu giá trị không được khai báo trong danh sách type parameter. Trước Go 1.18, chỉ có các kiểu thông thường.

Generic tùy chỉnh của Go không được triển khai như các template văn bản code đơn giản. Đây là một khác biệt nền tảng so với việc sinh code. Trong lập trình Go có một quy tắc cơ bản: mọi expression có kiểu đều phải có một kiểu được xác định, có thể là một kiểu thông thường hoặc một type parameter.

Ví dụ, trong đoạn code sau, chỉ function dot không compile. các function còn lại đều compile bình thường. Lý do rất đơn giản:

  • trong function foo, kiểu của x là T, một type parameter. Chắc chắn rằng trong các lần sử dụng function, x có thể được khởi tạo với kiểu int hoặc string, nhưng điều đó không thay đổi sự thật rằng, theo góc nhìn của compiler, kiểu của nó là một type parameter.
  • trong function bar, kiểu của x[i] và x[y] đều là một type parameter, E.
  • trong function win, kiểu của x[1] và x[y] đều là một kiểu thông thường được xác định, int.
  • trong function dot, kiểu của x[1] và x[y] có thể là int hoặc string (hai kiểu thông thường khác nhau), dù chúng luôn giống hệt nhau.
func foo[T int | string](x T) {
	var _ interface{} = x // okay
}

func bar[T []E, E any](x T, i, j int) () {
	x[i] = x[j] // okay
}

func win[T ~[2]int | ~[8]int](x T, i, j int) {
	x[i] = x[j] // okay
}

func dot[T [2]int | [2]string](x T, i, j int) {
	x[i] = x[j]      // error: invalid operation
	var _ any = x[i] // error: invalid operation
}

Các element của string được xem là byte, nên code sau compile được,

func ele[ByteSeq ~string|~[]byte](x ByteSeq, n int) {
	_ = x[n] // okay
}

Vì cùng lý do (quy tắc cơ bản), trong đoạn code sau, cả hai function nop và jam đều compile bình thường, nhưng function mud thì không.

func nop[T *Base, Base int32|int64](x T) {
	*x = *x + 1 // okay
}

func jam[T int32|int64](x *T) {
	*x = *x + 1 // okay
}

func mud[T *int32|*int64](x T) {
	*x = *x + 1 // error: invalid operation
}

Tương tự, trong đoạn code sau, chỉ function box không compile, hai function còn lại đều compile bình thường.

func box[T chan int | chan byte](c T) {
	_ = <-c // error
}


func sed[T chan E, E int | byte](c T) {
	_ = <-c // okay
}

type Ch <-chan int
func cat[T chan int | Ch](c T) {
	_ = <-c // okay
}

Có thể type assert type parameter

Vì type parameter là một kiểu được xác định, nó có thể được type assert. Code sau compile được, ngay cả khi tại runtime có các expression kiểu case trùng nhau trong block code type-switch bên trong function wua.

import "fmt"

func nel[T int | string](x any) {
	if v, ok := x.(T); ok {
		fmt.Printf("x is a %T\n", v)
	} else {
		fmt.Printf("x is not a %T\n", v)
	}
}

func wua[T int | string](x any) {
	switch v := x.(type) {
	case T:
		fmt.Println(v)
	case int:
		fmt.Println("int")
	case string:
		fmt.Println("string")
	}
}

Không được dùng type parameter làm kiểu của named constant (cục bộ)

Điều đó có nghĩa là mọi giá trị của type parameter đều không phải constant.

Ví dụ, function sau không compile.

func f[P int]() {
	const y P = 5 // error: invalid constant type P
}

Sự thật này sẽ không bao giờ thay đổi.

Do sự thật này, việc convert một constant sang type parameter tạo ra một giá trị không phải constant của argument được truyền vào type parameter. Ví dụ, trong code sau, function h compile được, nhưng function g thì không.

const N = 5

func g[P int]() {
	const _ = P(N) // error: P(N) is not constant
}

func h[P int]() {
	var _ = P(N) // okay
}

Do quy tắc convert, kết quả trả về của hai function mud và tex khác nhau.

package main

const S = "Go"

func mud() byte {
	return 64 << len(string(S)) >> len(string(S))
}

func tex[T string]() byte {
	return 64 << len(T(S)) >> len(T(S))
}

func main() {
	println(mud()) // 64
	println(tex()) // 0
}

Hãy đọc bài viết strings trong Go và issue này để biết vì sao hai function trả về các kết quả khác nhau.

Function của một type parameter chỉ có thể được gọi khi tất cả các kiểu trong type set của type parameter đó có cùng một underlying type

Ví dụ, hiện tại (Go 1.25), trong code sau, các function foo và bar không compile, nhưng function tag thì có.

func foo[F func(int) | func(any)] (f F, x int) {
	f(x) // error: invalid operation: cannot call non-function f
}

func bar[F func(int) | func(int)int] (f F, x int) {
	f(x) // error: invalid operation: cannot call non-function f
}

type Fun func(int)

func tag[F func(int) | Fun] (f F, x int) {
	f(x) // okay
}

Không rõ quy tắc này có được nới lỏng trong các phiên bản Go tương lai hay không.

Nếu kiểu T trong composite literal là một type parameter, thì tất cả các kiểu trong type set của type parameter đó phải có cùng một underlying type

Ví dụ, hiện tại (Go 1.25), trong đoạn code sau, các function foo và bar compile bình thường, nhưng các function còn lại thì không.

func foo[T ~[]int] () {
	_ = T{}
}

type Ints []int

func bar[T []int | Ints] () {
	_ = T{} // okay
}

func ken[T []int | []string] () {
	_ = T{} // error: invalid composite literal type T
}

func jup[T [2]int | map[int]int] () {
	_ = T{} // error: invalid composite literal type T
}

Một phép toán index element yêu cầu type set của operand container không đồng thời chứa map và non-map

Và nếu tất cả các kiểu trong type set là map, thì underlying type của chúng phải giống hệt nhau. Nếu không, kiểu element của chúng phải giống hệt nhau. Các element của string được xem là các giá trị byte.

Ví dụ, hiện tại (Go 1.25), trong đoạn code sau, chỉ các function foo và bar compile bình thường.

func foo[T []byte | [2]byte | string](c T) {
	_ = c[0] // okay
}

type Map map[int]string
func bar[T map[int]string | Map](c T) {
	_ = c[0] // okay
}

func lag[T []int | map[int]int](c T) {
	_ = c[0] // invalid operation: cannot index c
}

func vet[T map[string]int | map[int]int](c T) {
	_ = c[0] // invalid operation: cannot index c
}

Hạn chế này có thể được loại bỏ trong các phiên bản Go tương lai (thực ra đây chỉ là hy vọng của tôi, tôi không chắc về điều này).

Nếu kiểu của index expression là một type parameter, thì tất cả các kiểu trong type set của nó phải là kiểu số nguyên. Function sau compile bình thường.

func ind[K byte | int | int16](s []int, i K) {
	_ = s[i] // okay
}

Suy ra một slice từ một giá trị của type parameter yêu cầu tất cả các kiểu trong type set của type parameter đó có cùng một underlying type

Ví dụ, hiện tại (Go 1.25), cả hai function sau đều không compile, ngay cả khi các phép toán subslice đều hợp lệ với mọi kiểu trong type set tương ứng.

func foo[T []int | [2]int](c T) {
	_ = c[:] // cannot slice c
}

func bar[T [8]int | [2]int](c T) {
	_ = c[:] // cannot slice c
}

Hạn chế này có thể được loại bỏ trong các phiên bản Go tương lai (một lần nữa, đây chỉ là hy vọng của tôi, thực ra tôi không chắc về điều này).

Lưu ý rằng việc suy ra từ một giá trị của type parameter mà type set của nó chỉ chứa các kiểu string và byte slice được cho phép. Ví dụ, function sau compile bình thường.

func lol[T string | []byte](c T) {
	_ = c[:] // okay
}

Nếu container được range trong vòng lặp for-range là một type parameter, thì tất cả các kiểu trong type set của type parameter đó phải có cùng một underlying type

Ví dụ, hiện tại (Go 1.25), trong code sau, chỉ hai function cuối, dot1 và dot2, compile bình thường.

func values[T []E | map[int]E, E any](kvs T) []E {
	r := make([]E, 0, len(kvs))
	// error: cannot range over kvs
	for _, v := range kvs {
		r = append(r, v)
	}
	return r
}

func keys[T map[int]string | map[int]int](kvs T) []int {
	r := make([]int, 0, len(kvs))
	for k := range kvs { // error: cannot range over kvs
		r = append(r, k)
	}
	return r
}

func sum[M map[int]int | map[string]int](m M) (sum int) {
	for _, v := range m { // error: cannot range over m
		sum += v
	}
	return
}

func foo[T []int | []string] (v T) {
	for range v {} // error: cannot range over v
}

func bar[T [3]int | [6]int] (v T) {
	for range v {} // error: cannot range over v
}

type MyInt int

func cat[T []int | []MyInt] (v T) {
	for range v {} // error: cannot range over v
}

type Slice []int

func dot1[T []int | Slice] (v T) {
	for range v {} // okay
}

func dot2[T ~[]int] (v T) {
	for range v {} // okay
}

Hạn chế này là có chủ ý. Theo tôi, mục đích của nó là bảo đảm cả hai iteration variable luôn có một kiểu được xác định (hoặc là một kiểu thông thường, hoặc là một kiểu type parameter). Tuy nhiên, hạn chế này quá chặt đối với mục đích đó. Vì trên thực tế, kiểu key hoặc kiểu element của một số container là giống nhau, ngay cả khi underlying type của các container khác nhau. Và trong nhiều trường hợp sử dụng, một trong hai iteration variable bị bỏ qua.

Tôi không chắc hạn chế này có được loại bỏ trong các phiên bản Go tương lai hay không. Theo ý kiến của tôi, hạn chế này làm giảm phần nào tính hữu ích của generic tùy chỉnh trong Go.

Nếu tất cả các kiểu có thể có là slice và array, và kiểu element của chúng giống nhau, ta có thể dùng các vòng lặp for thông thường để tránh hạn chế này.

func cat[T [3]int | [6]int | []int] (v T) {
	for i := 0; i < len(v); i++ { // okay
		_ = v[i] // okay
	}
}

Lời gọi function predeclared len ở đây là hợp lệ. Một section sau sẽ nói về điều này.

Code sau cũng không compile, nhưng điều đó là hợp lý. Vì các element được iterate của string là các giá trị rune, trong khi các element được iterate của []byte là các giá trị byte.

func mud[T string | []byte] (v T) {
	for range v {} // error: cannot range over v
}

Nếu mục đích là iterate các byte trong byte slice hoặc string, ta có thể dùng code sau để đạt được mục tiêu.

func mud[T string | []byte] (v T) {
	for range []byte(v) {} // okay
}

Phép convert []byte(v) (nếu nó theo sau keyword range) được official standard Go compiler tối ưu hóa riêng để không duplicate các byte underlying.

Function sau hiện tại không compile (Go 1.25), ngay cả khi kiểu của hai iteration variable luôn là int và rune. Không rõ nó có compile trong các phiên bản Go tương lai hay không.

func aka[T string | []rune](runes T) {
	for i, r := range runes { // cannot range over runes
		_ = i
		_ = r
	}
}

Các phép convert có type parameter tham gia

Trước hết, ta cần biết các quy tắc convert đối với kiểu/giá trị thông thường.

Theo đặc tả hiện tại (Go 1.25), cho hai kiểu From và To, giả sử ít nhất một trong hai là type parameter, thì một giá trị của From có thể được convert sang To nếu một giá trị của mỗi kiểu trong type set của From có thể được convert sang mỗi kiểu trong type set của T (lưu ý rằng type set của một kiểu thông thường chỉ chứa chính kiểu thông thường đó).

Ví dụ, tất cả các function sau đều compile bình thường.

func pet[A ~int32 | ~int64, B ~float32 | ~float64](x A, y B){
	x = A(y)
	y = B(x)
}

func dig[From ~byte | ~rune, To ~string | ~int](x From) To {
	return To(x)
}

func cov[V ~[]byte | ~[]rune](x V) string {
	return string(x)
}

func voc[V ~[]byte | ~[]rune](x string) V {
	return V(x)
}

Nhưng function sau không compile, vì các giá trị string không thể được convert sang int.

func eve[X, Y int | string](x X) Y {
	return Y(x) // error
}

Function sau không compile, ngay cả khi phép convert trong nó hợp lệ với mọi type argument có thể có. Lý do là []T là một kiểu thông thường, không phải type parameter, và underlying type của nó chính là nó. Không có quy tắc nào cho phép convert các giá trị từ []T sang string.

func jon[T byte](x string) []T {
	return []T(x) // error
}

Các phiên bản Go tương lai có thể nới lỏng các quy tắc để làm cho phép convert trong ví dụ trên hợp lệ.

Khi dùng official standard Go compiler, trong program sau,

  • các function tup và pad không compile. Lý do là các giá trị có kiểu AgePtr không thể được convert trực tiếp sang *int.
  • cả ba function generic còn lại đều compile bình thường. Tuy nhiên, function dot không nên compile theo quy tắc đã mô tả ở trên. Đây có thể là một bug của standard compiler, hoặc quy tắc được mô tả trong đặc tả Go hiện tại cần một điều chỉnh nhỏ.
package main

type Age int
type AgePtr *Age

func dot[T ~*Age](x T) *int {
	return (*int)(x) // okay
}

func tup(x AgePtr) *int {
	// error: cannot convert x (variable of type AgePtr)
	//        to type *int
	return (*int)(x)
}

func tup2(x AgePtr) *int {
	return (*int)((*Age)(x))
}

func pad[T AgePtr](x T) *int {
	// error: cannot convert x to type *int
	return (*int)(x)
}

func pad2[T AgePtr](x T) *int {
	return (*int)((*Age)(x))
}

func main() {
	var x AgePtr
	var _ = dot[AgePtr](x)
	var _ = tup2(x)
	var _ = pad2[AgePtr](x)
}

Các phép gán có type parameter tham gia

Trước hết, ta cần biết các quy tắc gán đối với kiểu/giá trị thông thường.

Trong các mô tả sau, kiểu của giá trị đích được gọi là kiểu đích, và kiểu của giá trị nguồn được gọi là kiểu nguồn.

Theo đặc tả hiện tại (Go 1.25), đối với một phép gán có type parameter tham gia,

  • nếu kiểu đích là một type parameter và giá trị nguồn là một giá trị không có kiểu, thì phép gán chỉ hợp lệ khi giá trị không có kiểu đó assignable cho mọi kiểu trong type set của type parameter đích.
  • nếu kiểu đích là một type parameter nhưng kiểu nguồn là một kiểu thông thường, thì phép gán chỉ hợp lệ khi kiểu thông thường nguồn là kiểu không có tên và các giá trị của nó assignable cho mọi kiểu trong type set của type parameter đích.
  • nếu kiểu nguồn là một type parameter nhưng kiểu đích là một kiểu thông thường, thì phép gán chỉ hợp lệ khi kiểu thông thường đích là kiểu không có tên và các giá trị của mọi kiểu trong type set của type parameter nguồn assignable cho kiểu thông thường đích.
  • nếu cả kiểu đích và kiểu nguồn đều là type parameter, thì phép gán không hợp lệ.

Từ các quy tắc trên, ta có thể thấy rằng giá trị của một kiểu có tên không thể được gán cho một kiểu có tên khác.

Trong đoạn code sau, có bốn phép gán không hợp lệ.

func dat[T ~int | ~float64, S *int | []bool]() {
	var _ T = 123 // okay
	var _ S = nil // okay
}

func zum[T []byte](x []byte) {
	var t T = x // okay
	type Bytes []byte
	var y Bytes = x // okay (cả hai đều là kiểu thông thường)
	x = t // okay
	x = y // okay
	
	// Cả hai đều là kiểu có tên.
	t = y // error
	y = t // error
	
	// Để làm cho hai phép gán trên hợp lệ,
	// các giá trị nguồn trong đó phải được convert.
	t = T(y)     // okay
	y = Bytes(t) // okay
}


func pet[A, B []byte](x A, y B){
	// Cả hai đều là type parameter.
	x = y // error: cannot use y as type A in assignment
	y = x // error: cannot use x as type B in assignment
}

Không rõ các quy tắc gán có được nới lỏng trong các phiên bản Go tương lai hay không. Có vẻ khả năng này là thấp.

Các lời gọi function predeclared

Sau đây là một số quy tắc và chi tiết về lời gọi một số function predeclared khi có type parameter tham gia.

Lời gọi function predeclared len hoặc cap hợp lệ nếu nó hợp lệ với mọi kiểu trong type set của argument

Trong đoạn code sau, function capacity không compile, hai function còn lại đều compile bình thường.

type Container[T any] interface {
	~chan T | ~[]T | ~[8]T | ~*[8]T | ~map[int]T | ~string
}

func size[T Container[int]](x T) int {
	return len(x) // okay
}

func capacity[T Container[int]](x T) int {
	return cap(x) // error: invalid argument x for cap
}

func capacity2[T ~chan int | ~[]int](x T) int {
	return cap(x) // okay
}

Lưu ý rằng lời gọi len hoặc cap luôn trả về một giá trị không phải constant nếu kiểu của argument trong lời gọi là một type parameter, ngay cả khi type set của argument chỉ chứa array và pointer tới array. Ví dụ, trong code sau, lời gọi cap và len đầu tiên trong hai function đầu đều không compile.

func f[T [2]int](x T) {
	const _ = cap(x) // error: cap(x) is not constant
	const _ = len(x) // error: len(x) is not constant

	var _ = cap(x) // okay
	var _ = len(x) // okay
}

func g[P *[2]int](x P) {
	const _ = cap(x) // error: cap(x) is not constant
	const _ = len(x) // error: len(x) is not constant

	var _ = cap(x) // okay
	var _ = len(x) // okay
}

func h(x [2]int) {
	const _ = cap(x) // okay
	const _ = len(x) // okay
	const _ = cap(&x) // okay
	const _ = len(&x) // okay
}

Quy tắc này có thể được thay đổi. Nhưng nói thật, khả năng này rất thấp. Cá nhân tôi cho rằng hành vi hiện tại hợp lý hơn.

Do quy tắc này, hai function sau trả về các kết quả khác nhau.

package main

const S = "Go"

func ord(x [8]int) byte {
	return 1 << len(x) >> len(x)
}

func gen[T [8]int](x T) byte {
	return 1 << len(x) >> len(x)
}

func main() {
	var x [8]int
	println(ord(x), gen(x)) // 1 0
}

Một lần nữa, hãy đọc bài viết strings trong Go và issue này để biết vì sao hai function trả về các kết quả khác nhau.

Lưu ý rằng function sau không compile, vì kiểu của &x là *T, một pointer tới một type parameter, thay vì pointer tới một array.

func e[T [2]int]() {
	var x T
	var _ = len(&x) // invalid argument: &x for len
	var _ = cap(&x) // invalid argument: &x for cap
}

Nói cách khác, một type parameter mà type set của nó chỉ chứa một kiểu không tương đương với chính kiểu duy nhất đó. Type parameter có tính hai mặt sóng-hạt. Trong một số tình huống, nó hoạt động như các kiểu trong type set của nó. Trong một số tình huống khác, nó hoạt động như một kiểu riêng biệt. Cụ thể hơn, một type parameter hoạt động như một kiểu riêng biệt (không có underlying type chung với bất kỳ kiểu nào khác) khi nó được dùng làm một thành phần của kiểu tổ hợp. Trong ví dụ trên, *T và *[2]int là hai kiểu thông thường khác nhau.

Lời gọi function predeclared new không có yêu cầu thêm đối với argument

Function sau compile bình thường.

func MyNew[T any]() *T {
	return new(T)
}

Nó tương đương với

func MyNew[T any]() *T {
	var t T
	return &t
}

Yêu cầu đối với lời gọi function predeclared make khi argument thứ nhất là một type parameter

Yêu cầu đối với type set của type parameter:

  • Tất cả các kiểu trong type set phải có cùng một underlying type, hoặc
  • Tất cả các kiểu trong type set phải là kiểu channel có cùng kiểu element và hướng của channel không được xung đột (type set không được đồng thời chứa channel chỉ nhận và channel chỉ gửi).

Hiện tại (Go 1.25), trong đoạn code sau, cả hai function voc và ted đều không compile, hai function còn lại compile bình thường.

func voc[T chan bool | chan int]() {
	_ = make(T) // error: invalid argument: cannot make T
}

func ted[T chan<- int | <-chan int]() {
	_ = make(T) // error: invalid argument: cannot make T
}

type Stream chan int
type Queue Stream

func fat[T Stream | chan int | Queue | chan<- int]() {
	_ = make(T) // okay
}

func nub[T Stream | chan int | Queue | <-chan int]() {
	_ = make(T) // okay
}

Theo cách hiểu của tôi, yêu cầu này nhằm làm cho các phép toán tiếp theo trên các container được tạo (chúng là channel trong ví dụ trên) luôn hợp lệ. Ví dụ, để bảo đảm một giá trị nhận từ channel được tạo có một kiểu được xác định (hoặc là một type parameter, hoặc là một kiểu thông thường).

Cá nhân tôi cho rằng yêu cầu này quá chặt. Sau cùng, trong một số trường hợp, các phép toán tiếp theo được giả định đó không xảy ra.

Do cùng yêu cầu đó, cả hai function sau cũng không compile.

func zig[T ~[]int | map[int]int](c T) {
	_ = make(T) // error: invalid argument: cannot make T
}

func rat[T ~[]int | ~[]bool](c T) {
	_ = make(T) // error: invalid argument: cannot make T
}

Lời gọi function predeclared new không có yêu cầu này.

Lời gọi function predeclared delete yêu cầu tất cả các kiểu trong type set của argument thứ nhất có cùng một kiểu key

Lưu ý, kiểu key giống nhau này có thể là kiểu thông thường hoặc kiểu type parameter.

Cả hai function sau đều compile bình thường.

func zuk[M ~map[int]string | ~map[int]bool](x M, k int) {
	delete(x, k)
}

func pod[M map[K]int | map[K]bool, K ~int | ~string](x M, k K) {
	delete(x, k)
}

Lời gọi function predeclared close yêu cầu tất cả các kiểu trong type set của argument là kiểu channel

Function sau compile bình thường.

func dig[T ~chan int | ~chan bool | ~chan<- string](x T) {
	close(x)
}

Các function predeclared complex, real và imag hiện không chấp nhận argument có kiểu type parameter

Việc gọi ba function này với argument là type parameter có thể phá vỡ quy tắc cơ bản được đề cập trong section đầu tiên của chương hiện tại.

Đây là một vấn đề mà thiết kế generic tùy chỉnh hiện tại không thể giải quyết. Đã có một issue cho vấn đề này.

Về các constraint có type set rỗng

Type set của một số kiểu interface có thể rỗng. Một kiểu interface có type set rỗng implement mọi kiểu interface, bao gồm chính nó.

Các kiểu interface có type set rỗng hoàn toàn vô dụng trong thực tế, nhưng chúng có thể ảnh hưởng đến mức độ hoàn thiện của triển khai xét từ góc nhìn lý thuyết.

Thực sự có một số điểm chưa hoàn thiện trong triển khai của official standard Go compiler hiện tại (v1.25.n).

Ví dụ sau đây là một ví dụ, trong đó mọi lời gọi function trong function g đều đáng lẽ compile bình thường. Tuy nhiên, hai lời gọi không compile với official standard Go compiler mới nhất (v1.25.n).

func f1[T any](x T) {}
func f2[T comparable](x T) {}
func f3[T []int](x T) {}
func f4[T int](x T) {}

// Đây là một kiểu interface có type set rỗng.
type C interface {
	[]int
	m()
}

func g[V C](v V) {
	f1(v) // okay
	f2(v) // error: V does not implement comparable
	f3(v) // okay
	f4(v) // error: V does not implement int
}

Đặc tả Go hiện tại nêu rõ:

Hạn chế triển khai: Compiler không bắt buộc phải báo lỗi nếu kiểu của một operand là một type parameter có type set rỗng. Các function có những type parameter như vậy không thể được khởi tạo; mọi nỗ lực khởi tạo sẽ dẫn đến lỗi tại vị trí khởi tạo.

Vì vậy, các điểm chưa hoàn thiện nêu trên không phải là bug của official standard Go compiler.
