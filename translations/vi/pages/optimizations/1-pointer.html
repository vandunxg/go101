Pointer

Tránh các phép kiểm tra pointer nil của array không cần thiết trong loop

Có một số thiếu sót trong implementation hiện tại của Go compiler tiêu chuẩn chính thức (v1.24.n). Một trong số đó là một số phép kiểm tra pointer nil của array không được đưa ra ngoài loop. Đây là một ví dụ cho thấy thiếu sót này.

// unnecessary-checks.go
package pointers

import "testing"

const N = 1000
var a [N]int

//go:noinline
func g0(a *[N]int) {
	for i := range a {
		a[i] = i // line 12
	}
}

//go:noinline
func g1(a *[N]int) {
	_ = *a // line 18
	for i := range a {
		a[i] = i // line 20
	}
}

func Benchmark_g0(b *testing.B) {
	for i := 0; i < b.N; i++ { g0(&a) }
}

func Benchmark_g1(b *testing.B) {
	for i := 0; i < b.N; i++ { g1(&a) }
}

Hãy chạy benchmark với tùy chọn compiler -S; các output sau đây thu được (đã lược bỏ những phần text không đáng chú ý):

Từ các output, có thể thấy implementation g1 có performance tốt hơn implementation g0, ngay cả khi implementation g1 có thêm một dòng code (line 18). Tại sao? Câu hỏi này được giải đáp bởi các assembly instruction được output.

Trong implementation g0, instruction TESTB được generate bên trong loop, còn trong implementation g1, instruction TESTB được generate bên ngoài loop. Instruction TESTB được dùng để kiểm tra argument a có phải là một pointer nil hay không. Với trường hợp cụ thể này, kiểm tra một lần là đủ. Dòng code thêm đó tránh được thiếu sót trong implementation của compiler.

Có một implementation thứ ba có performance tương đương implementation g1. Implementation thứ ba dùng một slice được tạo từ argument array pointer.

//go:noinline
func g2(x *[N]int) {
	a := x[:]
	for i := range a {
		a[i] = i
	}
}

Lưu ý rằng thiếu sót này có thể được sửa trong các version compiler tương lai.

Cũng lưu ý rằng nếu ba function implementation có thể được inline, kết quả benchmark sẽ thay đổi đáng kể. Đó là lý do các compiler directive //go:noinline được sử dụng ở đây. (Trước Go toolchain v1.18, các compiler directive //go:noinline thực sự không cần thiết ở đây. Vì Go toolchain v1.18 trở về trước không bao giờ inline một function có loop for-range.)

Trường hợp array pointer là một struct field

Đối với các trường hợp array pointer là một struct field, mọi thứ phức tạp hơn một chút. Dòng _ = *t.a trong code sau đây không có tác dụng trong việc tránh thiếu sót của compiler. Ví dụ, chênh lệch performance giữa function f1 và function f0 là nhỏ. (Thực tế, function f1 thậm chí có thể chậm hơn, nếu một instruction NOP được generate bên trong loop của nó.)

type T struct {
	a *[N]int
}

//go:noinline
func f0(t *T) {
	for i := range t.a {
		t.a[i] = i
	}
}

//go:noinline
func f1(t *T) {
	_ = *t.a
	for i := range t.a {
		t.a[i] = i
	}
}

Để đưa các phép kiểm tra pointer nil của array ra ngoài loop, nên copy field t.a vào một local variable, sau đó áp dụng mẹo được giới thiệu ở trên:

//go:noinline
func f3(t *T) {
	a := t.a
	_ = *a
	for i := range a {
		a[i] = i
	}
}

Hoặc đơn giản tạo một slice từ array pointer field:

//go:noinline
func f4(t *T) {
	a := t.a[:]
	for i := range a {
		a[i] = i
	}
}

Kết quả benchmark:

Benchmark_f1-4  637.4 ns/op
Benchmark_f2-4  511.3 ns/op
Benchmark_f3-4  390.1 ns/op
Benchmark_f4-4  387.6 ns/op

Kết quả xác nhận các kết luận trước đó.

Lưu ý, function f2 được nhắc đến trong kết quả benchmark được khai báo như sau

//go:noinline
func f2(t *T) {
	a := t.a
	for i := range a {
		a[i] = i
	}
}

Implementation f2 không nhanh bằng implementation f3 và f4, nhưng nhanh hơn implementation f0 và f1. Tuy nhiên, đó là một câu chuyện khác.

Nếu các element của array pointer field không bị sửa đổi (chỉ được đọc) trong loop, cách f1 có performance tương đương cách f3 và f4.

Theo quan điểm cá nhân, trong hầu hết trường hợp, nên thử dùng cách slice (cách f4) để đạt performance tốt nhất, vì nhìn chung slice được Go compiler tiêu chuẩn chính thức optimize tốt hơn array.

Tránh dereference pointer không cần thiết trong loop

Đôi khi, Go compiler tiêu chuẩn chính thức hiện tại (v1.24.n) chưa đủ thông minh để generate assembly instruction theo cách được optimize tốt nhất. Phải viết code theo một cách khác để đạt performance tốt nhất. Ví dụ, trong code sau đây, function f có performance kém hơn nhiều so với function g.

// avoid-indirects_test.go
package pointers

import "testing"

//go:noinline
func f(sum *int, s []int) {
	for _, v := range s { // line 8
		*sum += v // line 9
	}
}

//go:noinline
func g(sum *int, s []int) {
	var n = *sum
	for _, v := range s { // line 16
		n += v // line 17
	}
	*sum = n
}

var s = make([]int, 1024)
var r int

func Benchmark_f(b *testing.B) {
	for i := 0; i < b.N; i++ {
		f(&r, s)
	}
}

func Benchmark_g(b *testing.B) {
	for i := 0; i < b.N; i++ {
		g(&r, s)
	}
}

Các assembly instruction được output cho thấy pointer sum được dereference bên trong loop trong function f. Một phép dereference là một memory operation. Đối với function g, các phép dereference xảy ra bên ngoài loop, và các instruction được generate cho loop chỉ xử lý register. Việc để CPU instruction xử lý register nhanh hơn nhiều so với xử lý memory là lý do function g có performance tốt hơn nhiều so với function f.

Đây không phải là một thiếu sót của compiler. Thực tế, function f và g không tương đương (mặc dù trong hầu hết use case thực tế, kết quả của chúng giống nhau). Ví dụ, nếu chúng được gọi như trong code sau đây, chúng sẽ trả về các kết quả khác nhau (cảm ơn skeeto@reddit vì đã đưa ra sự sửa chữa này).

{
	var s = []int{1, 1, 1}
	var sum = &s[2]
	f(sum, s)
	println(*sum) // 6
}
{
	var s = []int{1, 1, 1}
	var sum = &s[2]
	g(sum, s)
	println(*sum) // 4
}

Một implementation khác có performance tốt cho trường hợp cụ thể này là đưa pointer parameter ra ngoài function body (một lần nữa, nó không hoàn toàn tương đương với function f hoặc g):

//go:noinline
func h(s []int) int {
	var n = 0
	for _, v := range s {
		n += v
	}
	return n
}

func use_h(s []int) {
	var sum = new(int)
	*sum += h(s)
	...
}
