Maps

Trong Go, về lý thuyết capacity của một map là không giới hạn; trên thực tế, nó chỉ bị giới hạn bởi memory khả dụng. Đó là lý do hàm built-in cap không áp dụng cho map.

Trong implementation runtime Go tiêu chuẩn chính thức, map được implement nội bộ dưới dạng hashtable. Mỗi map/hashtable duy trì một backing array để lưu các entry của map (các cặp key-value). Khi ngày càng có nhiều entry được đưa vào map, size của backing array có thể bị xem là quá nhỏ để lưu thêm entry, vì vậy một backing array mới lớn hơn sẽ được allocate và các entry hiện tại (trong backing array cũ) sẽ được chuyển sang đó, sau đó backing array cũ sẽ bị loại bỏ.

Trong implementation runtime Go tiêu chuẩn chính thức, backing array của một map sẽ không bao giờ shrink, ngay cả khi mọi entry đã bị delete khỏi map. Đây là một dạng lãng phí memory. Nhưng trên thực tế, điều này hiếm khi là vấn đề và thực ra thường tốt cho performance của chương trình.

Xóa các entry của map

Có thể dùng loop sau để xóa mọi entry trong một map:

	for key := range aMap {
		delete(aMap, key)
	}

Loop này được tối ưu đặc biệt (trừ khi tồn tại các entry có key là NaN), nên việc thực thi nó rất nhanh. Tuy nhiên, cần lưu ý rằng như đã đề cập ở trên, backing array của map đã được clear không shrink sau loop. Vậy làm thế nào để release backing array của map? Có hai cách:

	aMap = nil
	// hoặc
	aMap = make(map[K]V)

Nếu backing array của map không được tham chiếu ở nơi khác, cuối cùng backing array sẽ được garbage collector thu gom sau khi được release.

Nếu sẽ có nhiều entry mới được đưa vào map sau khi map được clear, cách thứ nhất được ưu tiên; nếu không, cách thứ hai (release) được ưu tiên.

Kể từ Go 1.21, có một cách tốt hơn để thực hiện việc này. Go 1.21 đã giới thiệu một hàm built-in mới, clear, có thể được dùng để xóa mọi entry trong một map, bao gồm cả những entry có key là NaN.

Lưu ý: hiện tại (Go toolchain 1.24), dùng hàm built-in clear để clear một map có ít nhất một entry mất thời gian tỷ lệ với size của backing array của map.

aMap[key]++ hiệu quả hơn aMap[key] = aMap[key] + 1

Trong statement aMap[key] = aMap[key] + 1, key được hash hai lần, nhưng trong statement aMap[key]++, nó chỉ được hash một lần.

Tương tự, aMap[key] += value hiệu quả hơn aMap[key] = aMap[key] + value.

Điều này có thể được chứng minh bằng code benchmark sau:

package maps

import "testing"

var m = map[int]int{}

func Benchmark_increment(b *testing.B) {
	for i := 0; i < b.N; i++ {
		m[99]++
	}
}

func Benchmark_plusone(b *testing.B) {
	for i := 0; i < b.N; i++ {
		m[99] += 1
	}
}

func Benchmark_addition(b *testing.B) {
	for i := 0; i < b.N; i++ {
		m[99] = m[99] + 1
	}
}

Kết quả benchmark:

Benchmark_increment-4  11.31 ns/op
Benchmark_plusone-4    11.21 ns/op
Benchmark_addition-4   16.10 ns/op

Pointer trong map

Nếu cả key type và element type của một map đều không chứa pointer, thì trong scan phase của một GC cycle, garbage collector sẽ không scan các entry của map. Điều này có thể tiết kiệm rất nhiều thời gian.

Gợi ý này cũng đúng với các loại container khác trong Go, chẳng hạn như slice, array và channel.

Dùng byte array thay cho string ngắn làm key

Nội bộ, mỗi string chứa một pointer trỏ tới các byte underlying của string đó. Vì vậy, nếu key type hoặc element type của một map là string type, thì mọi entry của map đều cần được scan trong các GC cycle.

Nếu có thể bảo đảm rằng các string value được dùng trong các entry của một map có một max length và max length đó nhỏ, thì có thể dùng array type [N]byte để thay thế các string type (trong đó N là max string length). Làm vậy sẽ tiết kiệm nhiều thời gian scan garbage collection nếu số lượng entry trong map rất lớn.

Ví dụ, trong code sau, các entry của mapB không chứa pointer, nhưng các key (string) của mapA chứa pointer. Vì vậy garbage collector sẽ skip mapB trong scan phase của một GC cycle.

	var mapA = make(map[string]int, 1 << 16)
	var mapB = make(map[[32]byte]int, 1 << 16)

Đồng thời, cần lưu ý rằng compiler tiêu chuẩn chính thức thực hiện các tối ưu hóa đặc biệt khi hash các map key có size là 4 hoặc 8 byte. Vì vậy, xét từ góc độ tiết kiệm CPU, tốt hơn là dùng map[[8]byte]V thay cho map[[5]byte]V, và tốt hơn là dùng map[int32]V thay cho map[int16]V.

Giảm tần suất modification của element map

Trong chapter "strings and byte slices" trước đó, đã đề cập rằng một conversion từ byte-slice sang string xuất hiện làm index key trong một expression truy xuất element của map không allocate, nhưng các conversion như vậy trong các L-value map element index expression sẽ allocate.

Vì vậy, đôi khi có thể giảm tần suất sử dụng các conversion như vậy trong các L-value map element index expression để cải thiện performance của chương trình.

Trong ví dụ sau, cách B (cách dùng pointer element) có performance tốt hơn cách A. Lý do là cách B modification các element value ít hơn. Các element trong cách B là pointer; một khi đã được tạo, chúng không bao giờ bị thay đổi.

package maps

import "testing"

var wordCounterA = make(map[string]int)
var wordCounterB = make(map[string]*int)
var key = make([]byte, 64)

func IncA(w []byte) {
	wordCounterA[string(w)]++
}

func IncB(w []byte) {
	p := wordCounterB[string(w)]
	if p == nil {
		p = new(int)
		wordCounterB[string(w)] = p
	}
	*p++
}

func Benchmark_A(b *testing.B) {
	for i := 0; i < b.N; i++ {
		for i := range key {
			IncA(key[:i])
		}
	}
}

func Benchmark_B(b *testing.B) {
	for i := 0; i < b.N; i++ {
		for i := range key {
			IncB(key[:i])
		}
	}
}

Kết quả benchmark:

Benchmark_A-4  11600 ns/op  2336 B/op  62 allocs/op
Benchmark_B-4   1543 ns/op     0 B/op   0 allocs/op

Mặc dù cách B tiêu tốn ít CPU hơn, nó tạo ra nhiều pointer, làm tăng burden của việc scan pointer trong một GC cycle. Nhưng nhìn chung, cách B hiệu quả hơn.

Có thể dùng thêm một counter table (một slice) và để map ghi các index vào table, nhằm tránh tạo nhiều allocation và nhiều pointer, như code sau đây cho thấy:

var wordIndexes = make(map[string]int)
var wordCounters []int

func IncC(w []byte) {
	if i, ok := wordIndexes[string(w)]; ok {
		wordCounters[i]++
	} else {
		wordIndexes[string(w)] = len(wordCounters)
		wordCounters = append(wordCounters, 1)
	}
}

func Benchmark_C(b *testing.B) {
	for i := 0; i < b.N; i++ {
		for i := range key {
			IncC(key[:i])
		}
	}
}

Kết quả benchmark:

Benchmark_A-4  11600 ns/op  2336 B/op  62 allocs/op
Benchmark_B-4   1543 ns/op     0 B/op   0 allocs/op
Benchmark_C-4   1609 ns/op     0 B/op   0 allocs/op

Xét trong thời gian ngắn, cách C gần như có performance tương đương cách B, nhưng vì dùng ít pointer hơn nhiều, trên thực tế nó hiệu quả hơn cách B khi xét trong thời gian dài.

Cần lưu ý rằng các kết quả benchmark ở trên cho thấy hai cách sau đều tạo ra zero allocation. Điều này thực ra không đúng. Chỉ là mỗi lần chạy benchmark của hai cách sau tạo ra trung bình ít hơn một allocation, nên bị truncate thành zero. Đây là một thiết kế có chủ ý của cách báo cáo benchmark trong các package tiêu chuẩn.

Cố gắng grow một map trong một bước

Nếu có thể dự đoán số lượng entry tối đa sẽ được đưa vào một map tại thời điểm viết code, nên tạo map bằng hàm make và truyền số lượng tối đa làm argument size của call make, để tránh phải grow map qua nhiều bước về sau.

Dùng index table thay cho map có key type chỉ có một tập nhỏ các value khả dĩ

Một số programmer thích dùng map có bool key để giảm việc sử dụng các code block if-else dài dòng. Ví dụ, code sau

	// Bên trong một function ...
	var condition bool
	condition = evaluateCondition()
	...
	if condition {
		counter++
	} else {
		counter--
	}
	...
	if condition {
		f()
	} else {
		g()
	}
	...

có thể được thay thế bằng

// Các map ở cấp package.
var boolToInt = map[bool]int{true: 1, false: 0}
var boolToFunc = map[bool]func(){true: f, false: g}

	// Bên trong một function ...
	var condition bool
	condition = evaluateCondition()
	...
	counter += boolToInt[condition]
	...
	boolToFunc[condition]()
	...

Nếu có nhiều code block if-else giống hệt như vậy được dùng trong code, việc dùng map có bool key sẽ giảm nhiều boilerplate và làm code trông sạch hơn. Với hầu hết use case, cách này nhìn chung là tốt. Tuy nhiên, tính đến Go toolchain v1.24.n, cách dùng map không thực sự hiệu quả xét từ góc độ performance khi thực thi code. Các benchmark sau cho thấy sự khác biệt về performance.

package maps

import "testing"

//go:noiline
func f() {}

//go:noiline
func g() {}

func IfElse(x bool) func() {
	if x {
		return f
	} else {
		return g
	}
}

var m = map[bool]func() {true: f, false: g}
func MapSwitch(x bool) func() {
	return m[x]
}

func Benchmark_IfElse(b *testing.B) {
	for i := 0; i < b.N; i++ {
		IfElse(true)()
		IfElse(false)()
	}
}

func Benchmark_MapSwitch(b *testing.B) {
	for i := 0; i < b.N; i++ {
		MapSwitch(true)()
		MapSwitch(false)()
	}
}

Kết quả benchmark:

Benchmark_IfElse-4      4.155 ns/op
Benchmark_MapSwitch-4  47.46 ns/op

Từ kết quả benchmark, có thể thấy cách dùng block if-else có performance tốt hơn nhiều so với cách dùng map-switch.

Với các use case yêu cầu performance code cao, có thể mô phỏng một map có bool key bằng cách dùng index table để giảm boilerplate if-else, nhưng vẫn giữ được sự đơn giản của cách map switch, với sự trợ giúp của một hàm bool-to-int. Các benchmark sau cho thấy cách dùng index table.

func b2i(b bool) (r int) {
	if b {
		r = 1
	}
	return
}

var boolMap = [2]func(){g, f}

func Benchmark_BoolMap(b *testing.B) {
	for i := 0; i < b.N; i++ {
		boolMap[b2i(true)]()
		boolMap[b2i(false)]()
	}
}

Từ code trên, có thể thấy cách dùng index table gần như sạch sẽ như cách map-switch, dù cần thêm một hàm b2i nhỏ. Và từ các kết quả benchmark sau, có thể biết rằng cách dùng index table có performance tương đương cách dùng block if-else.

Benchmark_IfElse-4      4.155 ns/op
Benchmark_MapSwitch-4  47.46 ns/op
Benchmark_BoolMap-4     4.135 ns/op
